# Reusable arbitrary-length FFT plans

## Research question

The legacy arbitrary-length APIs prove correctness and expose algorithm structure, but they rebuild chirps, permutations, convolution kernels, radix-2 twiddles, and temporary vectors on every call. That makes them inappropriate baselines for steady-state comparison with reused FFTW plans.

This milestone asks:

1. how much reusable precomputation changes Bluestein and Rader execution cost;
2. when planned Rader beats planned Bluestein for prime lengths;
3. how the factorization of `p-1` changes Rader's convolution cost;
4. how quickly each plan repays its setup cost relative to the legacy API;
5. how the first-principles planned reductions compare with persistent FFTW `ESTIMATE` and `MEASURE` plans under matched normalization and lifecycle semantics.

The central principle is the same as the v3/v4 planning work: **setup cost and steady-state execution are different response variables**.

## Bluestein plan

For the forward DFT,

`X[k] = sum_n x[n] exp(-2 pi i n k / N)`.

Using

`2nk = n^2 + k^2 - (n-k)^2`,

Bluestein rewrites this as

`X[k] = c[k] * sum_n (x[n] c[n]) * conj(c[k-n]))`,

where

`c[j] = exp(-pi i j^2 / N)`.

The sum is a convolution. `BluesteinPlan(N)` chooses

`M = next_pow2(2N - 1)`,

precomputes the N chirp values and the M-point FFT of the symmetric convolution kernel, and owns a reusable `Radix2Plan(M)`. Each execution therefore requires only:

- packing/multiplying the input by the chirp;
- one planned M-point forward FFT;
- M pointwise complex products;
- one planned M-point inverse FFT;
- the final chirp multiplication.

The caller supplies an M-complex scratch vector. No dynamic allocation or trigonometric evaluation occurs during planned execution.

Inverse transforms use the identity

`IDFT(x) = conj(DFT(conj(x))) / N`,

so the same forward kernel spectrum is reused rather than storing a second convolution kernel.

## Rader plan

For prime `p`, choose a primitive root `g` modulo `p`. The nonzero input and output indices are generated by powers of `g`. The DFT can be written

`X[g^m] = x[0] + sum_q x[g^(-q)] exp(-2 pi i g^(m-q) / p)`,

which is a cyclic convolution of length

`L = p - 1`.

`RaderPlan(p)` precomputes:

- the output permutation `g^m mod p`;
- the inverse input permutation `g^(-q) mod p`;
- the forward convolution-kernel spectrum;
- the radix-2 convolution plan.

### Direct cyclic special case

When `L = p-1` is already a power of two, the cyclic convolution is evaluated directly with an L-point FFT. This is materially different from the legacy implementation, which always linearizes the convolution and zero-pads it.

For example:

| p | Bluestein M | planned Rader M |
|---:|---:|---:|
| 17 | 64 | 16 |
| 257 | 1024 | 256 |
| 65537 | 262144 | 65536 |

These are Fermat-prime examples, but the optimization applies to any prime whose predecessor is a power of two.

When `p-1` is not a power of two, the current implementation uses

`M = next_pow2(2(p-1) - 1)`

to evaluate a linear convolution and folds the `2L-1` result modulo L. This keeps the implementation dependency-free and reuses the existing radix-2 planner. A future mixed-radix convolution planner may reduce that padding cost.

Inverse transforms again use the conjugation identity, so only one kernel spectrum is persistent.

## ArbitraryPlan dispatch

`ArbitraryPlan` provides one reusable interface:

- power of two -> `Radix2Plan`;
- non-power-of-two prime -> `RaderPlan`;
- other lengths -> `BluesteinPlan`.

Explicit `Bluestein` and `Rader` policies remain available. The automatic prime choice is deliberately inspectable and should not be treated as a universal performance theorem. The formal benchmark keeps both prime reductions explicit so evidence can challenge the policy rather than being hidden by it.

## Buffer and memory contract

All complex values are `std::complex<double>` and caller buffers are ordinary `std::vector` storage.

### Bluestein

Persistent element payload:

- N chirp complex values;
- M kernel-spectrum complex values;
- M/2 radix-2 twiddles;
- M radix-2 permutation indices.

On a typical 64-bit ABI with 16-byte complex doubles and 8-byte `size_t`, this is approximately

`16N + 32M bytes`,

excluding vector capacity/object/allocator overhead.

Execution requires one caller-owned M-complex scratch vector: approximately `16M` bytes.

### Rader

Persistent element payload:

- M kernel-spectrum complex values;
- M/2 radix-2 twiddles;
- 2(p-1) Rader permutation indices;
- M radix-2 permutation indices.

Approximate payload:

`32M + 16(p-1) bytes`,

again excluding container/allocator overhead.

Execution requires one caller-owned M-complex scratch vector.

The larger persistent state is intentional: this milestone measures the memory-for-repeated-throughput tradeoff rather than pretending precomputation is free.

## Correctness contract

The dedicated self-test covers arbitrary, prime, composite, and power-of-two sizes. Planned Bluestein and `ArbitraryPlan` are compared against an independent direct DFT. Planned Rader is additionally exercised for every tested prime. Each path is also checked by forward/inverse round trip.

When FFTW is available, the benchmark executable cross-checks complete frequency-domain output at N=17, 127, and 509 before formal timing.

FMA/vector-width changes are not part of this milestone; numerical differences therefore remain dominated by the reduction and radix-2 path rather than a new ISA implementation.

## Formal benchmark semantics

The prime study uses N = 17, 31, 61, 127, 257, 509, 1009, and 4093.

Execution modes:

1. legacy Bluestein;
2. planned Bluestein;
3. legacy Rader;
4. planned Rader;
5. FFTW `ESTIMATE`;
6. FFTW `MEASURE`.

The two legacy modes deliberately retain their setup-inclusive API behavior and are used only to quantify the benefit of planning. Planned-vs-planned and planned-vs-FFTW comparisons use persistent plans.

For persistent execution modes:

- plans and buffers exist before timing;
- forward and inverse are timed as a pair, then divided by two;
- inverse normalization is inside the timed path for every backend;
- caller input/output/scratch buffers are reused;
- execution-mode order is randomized within every sample;
- transform-size order is randomized independently per session;
- a common calibrated iteration count is used within each size;
- every raw observation is retained.

Setup samples are separate. FFTW `MEASURE` setup is cold: wisdom is forgotten immediately before each measured forward+inverse plan pair. FFTW arrays are allocated outside setup timing.

## Hypotheses

H8. Persistent Bluestein and Rader plans will materially outperform the legacy setup-inclusive functions after only a small number of reused transforms.

H9. When `p-1` is a power of two, direct cyclic planned Rader will materially outperform planned Bluestein because its convolution FFT is substantially shorter.

H10. When both reductions use the same power-of-two convolution length, neither algorithm should be assumed universally faster: Rader's permutation/folding work and Bluestein's chirp multiplications create an implementation- and size-dependent crossover.

H11. FFTW will remain faster on most prime sizes because its planner/codelet system can exploit factorizations and generated kernels unavailable to the current first-principles reductions, but the gap should narrow in Rader's direct-cyclic special cases.

## Threats to validity

- The formal host is virtualized; prime-algorithm crossover claims are local to the recorded environment.
- The current Rader fallback uses radix-2 zero-padded convolution when `p-1` is not a power of two. A reusable mixed-radix convolution engine could change the result.
- `std::vector<std::complex<double>>` is not an FFTW-aligned allocation contract.
- FFTW `MEASURE` explores plans beyond a fixed Rader/Bluestein decomposition, so it is a production-library reference rather than an algorithm-isolation control.
- One random complex input family is used for timing. Numerical accuracy remains a separate research axis.
- Setup amortization depends on allocator/cache state and the exact plan constructor.

The checked-in result package records the exact source commit, binary hash, FFTW runtime, compiler/build, raw hashes, and randomized-session protocol.
